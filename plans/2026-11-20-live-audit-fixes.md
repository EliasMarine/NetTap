## Root cause of finding 2 (verified on the G11 today, read-only)
- `nettap-tshark` runs `tail -f /dev/null` as PID 1 (`init=<nil>`). Every supervised job (`container_exec.py` SUPERVISOR) backgrounds a watchdog `setsid sh -c 'sleep …; kill …'`, kills its group and exits without `wait`; the watchdog sh and its `sleep` are orphaned to PID 1, which never reaps.
- Host `ps`: 14,136 zombie children of the container's `tail` (14,039 `sleep`). cgroup `pids.current 14137`, `pids.max 14138`. `docker exec nettap-tshark sh -c …` fails with `sh: 1: Cannot fork`: every search, preview and analysis on the G11 is failing now.
- TShark 4.0.17 refuses the audit token (`… is neither a field nor a protocol name.`, exit 2). The search never compiles the filter first.

### PR A — `fix/pcap-search-reliability` (daemon + PCAP page)
Rounds 2–4 showed that a new start/poll protocol (job ids, legacy modes, generations, admission deadlines) creates more hazards than the audit asked us to remove. This revision keeps today's request contract (`GET /api/pcap/search?filter&from&to`, one current job, same key → that job, different key → replace) and fixes only what the audit found, plus the races this change itself would add.

1. **One compile routine, two callers.** `_compile_filter(filter)` = `validate_bpf_filter` (existing PCAP rules) + the existing CHECK_JOB compile; **the caller owns a reader slot**. `download_filtered` keeps its single slot and calls it as today. `check_filter(filter)` takes a slot (`reader_slot(…, 5 s)`) and calls it; it serves the new `POST /api/pcap/check-filter` (JSON body, so draft filters stay out of nginx's access log) and new-key search starts. Replies: 200 / 400 TShark's message / 503 busy / 500 couldn't check, the 5xx ones via `public_json` with fixed text, stderr to the daemon log only.
2. **Starts are admitted one at a time.** A new-key start takes `_start_lock` (an `asyncio.Lock`), runs `check_filter`, lists files and installs the job, all under the lock, so starts install in arrival order and an earlier start whose check finishes late can never overwrite a later one. A refused / busy / failed check installs nothing and leaves the current job alone. Polls for the current key never take the lock. Two tabs searching different filters behave as today (the later search replaces the earlier); see Out of scope.
3. **Replacing a job never cancels a read; one background read at a time.** Replacement no longer calls `task.cancel()`. The old job's loop checks before each file that it is still the current job and stops if not. All jobs share `_count_lock`: a job takes it, then a reader slot, then re-checks it is still current immediately before launching TShark. Background search therefore runs at most one TShark read at a time (two full-file reads can't share the 1 GiB container), and the second reader slot stays free for previews, analysis and checks.
4. **The count holds its slot until its reader ends.** The existing counter command stays (`docker exec nettap-tshark timeout -k 5 300 nice -n 19 tshark … -T fields -e frame.number`, so background priority is kept). The host-side `asyncio.wait_for(…, timeout+10)` that could return while the in-container reader still ran is replaced by waiting for the docker exec to end, which in-container `timeout -k 5 300` guarantees within 305 s of TShark starting (tini, from A0, reaps it). A host cap of 360 s remains only as a last resort (docker itself wedged): it kills the local client and logs an error. `shortcut:` a docker exec that starts more than 55 s late could outlive that cap; upgrade to a pgid kill if the log ever shows it.
5. **Streamed counting with lower bounds.** stdout is read in 64 KiB chunks and newline-terminated records are counted as they arrive (bounded memory; no list of frame numbers). The count observed so far survives every ending. Classification in order: exit 124, or 137 at/after the deadline → `timed_out(n)`; 137 before the deadline → `failed(n, out of memory)`; TShark's "cut short in the middle of a packet" text → `truncated(n)` (a file being written, or one left by a crash); exit 0 → `full(n)`; anything else → `failed(n, stderr)`. A result row appears for every file with `n > 0` and carries `complete: true` only for `full`; other rows show "at least n" and why. The job reports `files_full`, `files_truncated`, `failed`, `timed_out` and the first error. The search is labelled incomplete when `failed + timed_out > 0`; truncated files get their own line.
6. **Proxy budget.** `/api/pcap/search` and `/api/pcap/check-filter` get 60 s in `web/src/routes/api/[...path]/+server.ts` (a start: lock wait + 5 s slot + 15 s check + walk). If a browser gives up anyway, its start still installs later; that is the same user's search, and re-submitting the same filter returns it.
7. **Page (`web/src/routes/pcap/+page.svelte`, `web/src/lib/api/pcap.ts`).**
   - `searchPcaps` throws an error carrying the HTTP status.
   - The submitted search (filter, window) is one object. The results card names the submitted filter; previewing a result row uses the submitted filter.
   - A 400 shows TShark's message inline under the field (`aria-invalid`, `aria-describedby`) only while the input still holds the submitted text; otherwise as a page notice naming that filter. No results card, no count, no polls.
   - Preview: each preview is a snapshot `{file, filter, generation}`; render, title, Download and Retry use it; a response whose generation is no longer current (another selection, or Close) is dropped.
   - Download filtered is enabled only when the current input passed `POST /api/pcap/check-filter` (500 ms after typing stops; stale answers dropped). 400 disables it with the message; 503/500 leave it enabled with "Couldn't check the filter just now" (the download re-checks on the daemon).
   - Completion: incomplete → subtitle "· incomplete" and "Searched 7 of 318 files. 311 couldn't be searched: <first error>. Results are incomplete." Truncated files on their own line; "at least n" rows. "No matching packets found in any PCAP file" only when nothing was unread; otherwise "No matching packets in the files that could be searched."
8. **Tests.** pytest: refused filter → 400, no job, no count; couldn't check → 500 and busy → 503 through the error middleware; download with the other slot held still succeeds; two starts whose checks finish in reverse order install in arrival order; a refused start leaves the running job untouched; replacing a job never cancels its in-flight read, the old job stops before its next file, and a job replaced while waiting for `_count_lock` never launches; only one background read at a time while an interactive check gets the other slot; the slot stays held until the exec ends (a fake process that ends after the old host timeout); classification precedence incl. two frames then a read error → failed row "at least 2", two frames then timeout → timed_out with 2 kept, a closed truncated file as the only file with zero matches. Vitest: inline 400 only while the input matches; results card and row preview keep the submitted filter after an edit (mid-poll and after completion); previews completing in reverse order; Download filtered gating (400, 503); worker-start failure → "Searched 0 of N", incomplete; timeout-only → incomplete; truncated-only → not incomplete, its own line.
9. **`scripts/remote/deploy-pcap-search-fix.sh`** (template, `BRANCH=main`): pull, then resolve `TARGET=$(git rev-parse HEAD)` once; the build uses that checked-out tree. Before the first recreate, write `$REPO_DIR/.nettap-rollback-net347` (target commit, the running daemon and web image IDs) unless one already exists for this target, tag those IDs `nettap/…:rollback-net347`, and print restore commands generated from the record (retag, `up -d --no-deps --force-recreate`). Build daemon + web, recreate them `--no-deps`, wait healthy. Then `scripts/remote/verify_pcap_search.py` runs **inside the daemon container** (reads the token file; reference reads via `docker exec nettap-tshark`): `POST /api/pcap/check-filter` with `nettapqa_invalid_filter` → 400 naming it; a search with it → 400. Known-answer search: freeze a window over the newest 60 s of closed captures; take the daemon's file list for it (`GET /api/pcap/files`), non-empty; reference-count **every** listed file at `/pcap/<relative_path>` with `tshark -Y udp`, each exit 0; if all are 0, use `frame`; a positive reference is required. A reference failing on file damage (cut short) → try the previous 60 s window, up to 3 windows; a reader failure (fork, OOM, docker) → fail. Pass only when the search is `complete`, `files_checked == files_full == files_total == len(reference)`, `failed == timed_out == 0` and the {file: count} map of positive rows equals the reference. No usable window after 3 tries → fail. Then zombie children of the tshark PID 1 are 0. Non-zero exit on any failure.

## Key decisions & tradeoffs
- `init: true` over a SUPERVISOR rewrite: closes every orphan source, one line, a recreate with no data loss.
- Keep the search request contract and serialise starts with a lock, instead of job ids and generations: no client compatibility modes.
- Cooperative stop between files plus one background read at a time, instead of cancelling a read: no orphaned reader; a replaced search's last read may finish (≤ 305 s) before the new search's first read starts.
- Keep the `timeout`/`nice` counter and stream its stdout, instead of moving it onto `run_in_tshark`: keeps background priority and keeps observed counts on every ending.
- Download button gated by a debounced check instead of a check on click (popup blockers).
- Changelog names the loaded window rather than carrying the pick (a count links to a list over its own window, NET-160).
- Custom label: exact window in the pill instead of per-page text beside 14 selectors.

## Round 5 amendments (all Codex round 5 points accepted)
- **A2/A6 admission bound:** a new-key start has a 45 s monotonic deadline (proxy and nginx: 60 s). It waits for `_start_lock` only until the deadline. After taking the lock it re-checks the key: if the current job already has this key, it returns that job. It re-checks the deadline before installing; an expired start installs nothing and answers 503 "The search took too long to start; try again." The page's "Try again" resubmits the submitted search object with its **original** from/to, so a retry is the same key. Tests: a blocked first start, a duplicate waiter that gets the installed job, an expired waiter that installs nothing.
- **A4/A5 counter:** add `-l` (line-flushed) to the counter command, keeping `nice -n 19`. stdout and stderr are drained **concurrently** to EOF; stderr keeps a bounded sample (first 4 KiB) while still being read to the end. Tests: a child that writes more than a pipe's capacity to stderr before two frame numbers; two sparse matches then forced termination keep 2.
- **A7 coverage wording:** the notice describes coverage, not failure counts alone: "Fully searched 7 of 318 files. Reading stopped early in 2 files; 309 couldn't be read: <first error>. Results are incomplete." A file that failed after confirmed matches counts as "stopped early", with its row "at least n". Page test: one file, two confirmed matches, then a read error.
- **A9 verifier:** reference reads start only after the daemon's search is complete and no counting TShark (`frame.number`) is listed by `docker top nettap-tshark` (waits up to 330 s, so a pre-upgrade read has drained); reference reads run one at a time, each bounded to 300 s. The search poll gives up after 360 s without `files_checked` growing. Any expiry exits non-zero and prints the frozen window, checked/total and the first error.
- **Rollback:** the generated restore commands put back the recorded web **and** daemon images together (A0 stays). Daemon-only rollback is not offered, because the new page needs `POST /api/pcap/check-filter`.
- `shortcut:` a detached count after a wedged docker client (360 s cap) is outside `_count_lock`; recorded in the code comment with its upgrade path.
