# API calls without a session answer 401 JSON (NET-197)

## Problem

An `/api/*` call without a valid session got the same answer as a page: `302 → /login`, or `302 → /setup` during first run. The browser's `fetch` follows a redirect, so the caller received the login page's HTML with status **200**. Client code that trusts `res.ok` took that as success.

The NET-191 slice 3 review found one case: the own-rules editor showed "Saved" when nothing was sent (that card now checks the reply's shape). `packets.ts` and the Infrastructure page already worked around the same redirect with JSON-parse guards.

## Root cause

`handle` in `web/src/hooks.server.ts` had one answer for every unauthenticated request: a redirect. That suits a page the browser navigates to, not a JSON endpoint called with `fetch`.

## Fix

In `handle`, after the first-run allowlist check and before the first-run and login redirects: a request with no session whose path is `/api` or under it (`isUnder`, whole segments) gets `401` with `{"error":"Sign in first"}` and `content-type: application/json`. That reply is the `unauthorised()` helper, which the remote-function branch now uses too (its old inline `Response` is kept as OLD CODE).

Unchanged:

- `/api/health` is answered first, with no auth.
- `PUBLIC_PATHS`: `/login` and the three exact auth routes.
- First-run paths (`/api/setup/*`, `/api/bridge/*`) and `FIRST_RUN_REQUESTS` still resolve before the first admin exists.
- Pages still redirect to `/login`, or to `/setup` during first run.
- A request with a session.
- A damaged or unreadable user store never reopens setup: a page goes to `/login`, an API call gets 401.

During first run, an API call that isn't on the first-run list now gets 401, not `302 → /setup`. No session can exist then, and the setup page's HTML was the same bug.

No client changes. Clients already show `!res.ok` as an error, and `packets.ts` turns the 401 body into "Sign in first".

In the browser, the no-session API test fails on the old hook (`Expected: 401, Received: 200`, body `<!doctype html>`) and passes on the fix; the page-redirect and signed-in tests are guards and pass on both.

## Device check

`deploy-api-401.sh` rebuilds only `nettap-web`, then with no cookie through nginx needs `401 application/json` from `/api/suricata/rules/live`, `302` to `/login` from `/alerts` and `200` from `/api/health`. It prints status codes and content types only. Signing in afterwards is manual.

## Lessons

- A redirect is a page answer. `fetch` follows it silently, so a JSON endpoint must answer for itself with a status code the caller can see.
- Client-side guards (`packets.ts`, Infrastructure) were treating the symptom in two places; the hook is the one place that knows the request had no session.
- Run the browser harnesses, not only the type checks. The plan missed the first-run Go Live shell calls; only `npm run test:visual` showed them.
