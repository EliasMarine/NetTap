## Part 2. Findings

### HLT-1 — P1 — No health indicator checks the capture engines or ingest freshness; everything stays green when Zeek/Suricata/Logstash stop
- Evidence: capture health in every mode is link/promisc/routing only: bridge `BH:142-260, 642-666`, mirror `MM:245-326`, DHCP `dhcp_gateway_runtime.py:116-170`. No health path runs `docker inspect` on `nettap-zeek-live`, `nettap-suricata-live` or Logstash (the only container probes are `capture_control.py:153-178` for pcap-capture on the Settings tab, and version/upgrade code). System health = storage + SMART + `client.info()` only (`S:529-614`). Chip: `shell/status.ts:34-35` (green pulse on `normal`); Home: `HOME:122` (ok); Home's "no traffic" notice only fires when the whole selected range has 0 connections (`web/src/routes/+page.svelte:673`). Infrastructure's Zeek/Suricata stages turn `unknown` (never `failing`) at 0 events (`INF:983-987`); Logstash is `ok` whenever its API answers (`INF:1009-1012`).
- Failure scenario: Zeek crashes (or Logstash's pipeline wedges, or OpenSearch rejects writes) at 09:00. At 15:00 the sidebar chip still pulses green, Home shows Capture ok, Packets "No packets lost", System Healthy, OpenSearch Connected. The 24-hour charts still have data, so no notice appears. Nothing says "no new records since 09:00".
- Affected UI: sidebar capture chip, Home pipeline, System page health strip and overview chip.

### HLT-2 — P1 — "Packet loss" / "No packets lost" counts only kernel interface counters; capture-engine drops are never measured, and bridge mode reads br0
- Evidence: the loss window reads `rx_packets / rx_dropped / rx_missed_errors` of the capture interface only (`daemon/api/capture.py:82-93`, `loss_window.py:55-65`). A repository grep finds no use of Zeek `capture_loss`, Suricata `capture.kernel_drops`, or AF_PACKET or netsniff statistics anywhere in daemon or web. In bridge mode the interface is `br0` (`BCA:164-173`). br0 is a virtual device: its `rx_missed_errors` stays 0, so ring overruns on the physical member NICs are never counted (this is kernel behaviour, high confidence. Confirm by comparing `/sys/class/net/<member>/statistics/rx_missed_errors` with br0's). Wording: `capture.ts:99-103` ("No packets lost in the last 58 min · N received"), Home `HOME:150-151`, Infrastructure `INF:1319`. No caption says that drops inside Zeek, Suricata or netsniff are excluded.
- Failure scenario: at 900 Mbps Suricata's AF_PACKET ring drops 15 % of packets, and Zeek's `capture_loss.log` reports 8 %. The NIC delivered everything, so the UI says "No packets lost". The user trusts detections that are working from incomplete traffic. In bridge mode, an i226 ring overrun on enp2s0 also reads as zero loss.
- Affected UI: Home "Packets" stage, Infrastructure "Packet loss" KPI, cumulative loss row, and the Capture stage's ok/failing.

### HLT-3 — P2 — Bridge-mode "Promiscuous" and bypass state are inferred rather than read; bypass probably doesn't stop capture (suspected)
- Evidence: `promisc_enabled = link_up and not bypass_active` (`BCA:135`). Infrastructure prints "Promiscuous" whenever the bypass flag is false (`INF:977-980`), so br0's real IFF_PROMISC flag is never read. Bypass state lives in memory plus `/tmp/nettap-bypass-active` (`BH:38, 213`), which is the daemon's private tmpfs and is lost on restart. `/api/bridge/bypass/status` returns only the API instance's `_bypass_active` (`daemon/api/bridge.py:123-132`). Enabling bypass only runs `ip link set <member> promisc off` (`BH` trigger_bypass). The bridge driver keeps its own promiscuity count on ports, and capture listens on br0, so the UI's claim "Enable bypass? Capture will stop." (`BridgeStatus.svelte:340`) and "traffic is not being inspected" (`BH:242`) are probably false. **Suspected.** Confirm by enabling bypass, then checking `ip -d link show <member>` (promiscuity) and whether Zeek connection records keep arriving.
- Failure scenario: the owner enables bypass to stop inspection, and Zeek and Suricata carry on capturing. Separately, after a daemon restart during bypass, the UI shows bypass inactive and "Promiscuous" while the member NICs have promisc cleared.
- Affected UI: Infrastructure Capture stage, BridgeStatus bypass section.

### HLT-4 — P2 — An active bypass is displayed as "Capture status unknown"
- Evidence: bridge health returns `bypass` (`BH:657-658`). `captureChip` has no `bypass` case, so it falls to `default` → "Capture status unknown" (`shell/status.ts:42-43`). Home turns any status other than degraded/down into "Unknown" (`HOME:123-124`).
- Scenario: traffic is flowing uninspected (by design) and the shell shows a grey "unknown" instead of "Bypass: not inspecting".

### HLT-5 — P2 — Watchdog always shows "Inactive" in bridge mode
- Evidence: `_check_watchdog` runs `systemctl is-active nettap-watchdog` inside the daemon container (`BH:706-726`). The image installs no systemd (`docker/Dockerfile.daemon:21-35`) and the host systemd bus isn't mounted, so FileNotFoundError → False. Displayed as a red "Watchdog: Inactive" (`BridgeStatus.svelte:387-388`) and added as the issue "Watchdog service is not running" (`BH:243-244`).
- Scenario: the host watchdog is running, and every bridge-mode box reports its fail-safe as down. Alternatively the watchdog really is down and the UI can't tell the difference.

### HLT-6 — P2 — A capture interface that receives nothing is "normal"; no last-packet freshness
- Evidence: mirror health is normal when the link is up, carrier is present, promisc is on and there is no IP (`MM:307-312`). Bridge mode is the same idea (`BH:642-666`). Zero arrivals in the loss window give status `unknown` ("No packets in the last N min", `capture.ts:96`), which is neutral and never failing. No component tracks a last-packet or last-record time.
- Scenario: the switch SPAN session is removed or misconfigured. The chip stays a green pulsing "Mirror mode · enp2s0". Only a grey "No packets…" on Home hints at it.

### HLT-7 — P2 — System health "Healthy" ignores disk pressure and a storage-stopped capture
- Evidence: `_aggregate_health` counts storage only when `get_status` raises (`S:562-575, 522-526`). Usage ≥ 95 % with pcap-capture docker-stopped by the storage manager (`M:1022-1033, 953-956`) still yields `healthy`. The System page's separate Storage stage flags ≥ emergency (`SYS:283-295`), but Home's System stage and the overview chip say "Healthy".

### HLT-8 — P3 — A failed capture setup reads as "Capture not set up"
- `init_capture_manager` swaps in `CaptureManagerStub` on any exception (`main.py:564-580`). The stub reports `not_configured` with zero stats (`capture_mode_stub.py:67-87`), so the chip shows "Capture not set up" on a configured box whose `capture-mode.conf` is broken.

### HLT-9 — P3 — Bridge history statistics assume 30 s spacing
- `longest_downtime_seconds = streak * 30` (`BH:351`), but `check_health` is called by two loops (`main.py:383` and, through the adapter, `main.py:426`) and by every `/api/bridge/health` request (`daemon/api/bridge.py:27-31`), so streaks and `uptime_percentage` are per call, not per unit of time. These are exposed at `/api/bridge/stats` (client `web/src/lib/api/bridge.ts:125`). No rendering of them was found.

### HLT-10 — P3 — The Logstash stage is "ok" whenever its monitoring API answers (`INF:1009-1012`)
- Pipeline errors, back-pressure and failed outputs to OpenSearch are not considered.

### STO-1 — P1 — A storage-stopped full-packet capture can stay off indefinitely, with no UI signal
- Evidence: at ≥ 95 % the cascade `docker stop`s pcap-capture and writes a flag (`M:1022-1033, 953-956`). Deletion only aims below the emergency line: PCAP loop breaks at < 90 % (`M:890-891`), index emergency returns at < 90 % (`M:592-598`). Resume needs < 85 % (`M:1055-1065, 1800-1806`). In the 80–90 % band only `prune_oldest_indices` runs, and it deletes only indices **past their retention age** (`M:511-514, 1772-1779`). The flag file is read by nothing outside `M` (grep). The API and UI never expose it.
- Failure scenario: OpenSearch growth takes the disk to 95 %. pcap-capture is stopped and PCAP is deleted until usage reaches 89.9 %. ILM has nothing old enough to delete, so usage sits between 85 and 90 % and capture never resumes. Every time OpenSearch pushes it back to 90 %, more of the remaining PCAP history is deleted. The sidebar chip pulses green the whole time. Settings › Capture says only "Enabled — capture container not running", with no reason. PCAP for new alerts is silently unavailable for days.
- Affected UI: capture chip, Home, Settings › Capture, PCAP download features.

### STO-2 — P1 — A failed ILM verification at startup is never retried, and the card keeps showing "Policy synced"
- Evidence: `verify_ilm_policy` sets `_ilm_verified = True` as soon as `apply_ilm_policies_from_config` returns (`M:1140-1146`). That function catches every per-policy exception, including the connection or 403 error that `_get_existing_policy` re-raises (`daemon/storage/ilm.py:118-121, 444-447`), and returns `{"nettap-hot-policy": "error: …"}`. `run_cycle` retries only while `_ilm_verified` is False (`M:1721-1725`). The card's `synced` value comes from the **persisted** `ilm_applied.last_success` in retention.json (`retention_config.py:158, 247-250`; `M:1947-1956`). `handle_storage_status` overrides it only for an unapplied in-session save (`S:236-244`, revisions start equal).
- Failure scenario: OpenSearch is recreated (`down -v`) and comes up healthy but before its security bootstrap (403), or restarts while the daemon starts. The ISM policy is never created or attached. Settings shows "Policy synced" from last week, and the sidebar says "90-day retention". Indices are then deleted by age only once the disk reaches 80 % (`M:1772-1779`), so on a large disk data is kept for many months beyond the stated retention, which matters to an owner relying on it for privacy. The legacy `ilm_synced` field also reports True (`M:1931`).
- Affected UI: Settings › Retention health, sidebar retention text, System retention rows.

### STO-3 — P2 — Disk % ignores reserved blocks, so it is lower than df and than what OpenSearch can actually use
- Evidence: `check_disk_usage = used/total` from `shutil.disk_usage` (`M:297-304`, also `M:1847-1906`). `used` excludes ext4's reserved blocks (5 % by default) while `free` is `f_bavail`. OpenSearch's own disk guards are disabled (`docker/docker-compose.yml:109`), so OpenSearch (non-root) gets ENOSPC when `f_bavail` reaches 0, which is the daemon's "95 %".
- Scenario: a 1 TB disk shows "90 % used · 50 GB free" (the figures don't add up; df says 94.7 %). The "critical 95 %" capture stop fires only when non-root writers already have 0 bytes. With defaults the 90 % emergency normally acts first, so the practical risk is misleading figures, plus a thin margin.
- Affected UI: sidebar foot, System Storage card and stage, Settings Retention health, setup wizard.

### STO-4 — P2 — An emergency threshold above 95 % disables deletion at 95 % and over, while capture is stopped
- Evidence: validation allows emergency up to 99 (`retention_config.py:96-108`; UI `max={99}` at SET:1122). `critical_threshold` is fixed at 95 (`M:152`). In `run_cycle`, ≥ 95 % goes to `emergency_cascade` (`M:1750-1760`), which stops capture (`M:1022-1033`) but deletes only `if usage >= emergency_threshold` (`M:1041-1047`). The tiered-prune branch is skipped.
- Scenario: the owner sets emergency = 98 %. From 95 % to 98 % nothing is deleted, capture is stopped, Zeek and Suricata keep filling the disk, and OpenSearch reaches ENOSPC (STO-3) before any deletion runs.

### STO-5 — P2 — Retention and deletion failures are invisible; "Last prune" counts a failed cycle as done
- Evidence: `_delete_index` only logs (`M:457-465`). List failures return 0 (`M:481-485, 554-558`). PCAP unlink errors only log (`M:787-791, 825-829, 886-887`). `_last_prune_at` is stamped at the end of every cycle whatever happened (`M:1815`). `get_status` carries no last-error field. Settings › Retention health shows "Last prune 2m ago" and status healthy (SET:225-240, 1056-1061). The changelog records only `device_joined` and manual `storage_pruned` (`changelog.py:31-34`), so no automatic deletion, emergency cascade or capture stop is ever recorded where the owner can see it.
- Scenario: OpenSearch rejects deletes (403 after a recreate) for weeks. The card says healthy and nothing is aged out.

### STO-6 — P2 — Emergency prune and manual cleanup delete NetTap's audit log, and yesterday's still-written index
- Evidence: both select every dated non-dot index regardless of tier (`M:572-577`, `M:1466-1479`). `nettap-changelog-YYYY.MM.DD` (`changelog.py:45-55`) is tier `unknown` and sorts among the oldest, so it is deleted first in an emergency. Only "today (UTC)" is protected (`M:569-576`, `M:1471`). Yesterday's `arkime_sessions3-YYMMDD` can still receive late Zeek records stamped with the connection start time. Meanwhile the tiered prune skips `unknown` (`M:493-496`) and ILM doesn't cover `nettap-changelog-*` (`ilm_generator.py:28`), so outside emergencies the changelog is never aged.

### STO-7 — P3 — Emergency PCAP deletion can remove the file netsniff is writing
- `_delete_oldest_pcaps` has no newest-file guard (`M:880-891`), unlike `prune_pcaps_over_cap` (`M:822`). When OpenSearch, not PCAP, fills the disk, it deletes up to 500 files per cycle, possibly all of them, including the open one: that data is lost and its space isn't freed until rotation. It also runs outside `_cleanup_lock`, so it races manual cleanup (errors are logged only).

### STO-8 — P2 — The setup wizard shows fabricated disk figures and a hardcoded retention estimate
- Evidence: `GET /api/setup/storage` returns HTTP 200 with a mock (1000 GB total, 4.4 % used, `source:'mock'`) when the daemon doesn't answer (`web/src/routes/api/setup/storage/+server.ts:101-127`). `fetchStorage` in the wizard doesn't check `source` (`web/src/routes/setup/+page.svelte:480-495`) and renders it as real (`:1283-1300`). Settings and the wizard's requirements check do guard against it (SET:174; setup/+page.svelte:407). "Estimated retention capacity: N days at about 1.2 GB a day" uses the daemon's hardcoded `estimated_daily_gb: 1.2` (`M:1915`) and the formula free × threshold% / daily (`setup/+page.svelte:186-192`).
- Scenario: the daemon is still starting during setup. The owner sees "4.4 % used of 1000 GB, ≈ 760 days of retention" on a 256 GB disk.

### STO-9 — P2 — A manual cleanup that partly failed is shown as a success
- Evidence: the daemon returns 200 with `errors: ["Could not list indices, none deleted: …"]` (`M:1444-1448, 1479, 1525`). The UI shows "Cleanup complete: deleted 0 indices and N PCAP files, freed X. (1 errors)" in success styling and doesn't show the error text (SET:849-855).

### STO-10 — P2 — Shortening retention deletes data at once, with no preview or confirmation
- Evidence: a save re-generates the ISM policy (`ilm_generator.py:113-117`) and runs `add` plus `change_policy` on every existing matching index (`daemon/storage/ilm.py:167-210, 443`), so ISM deletes every index older than the new `hot_days` on its next run. The form saves on one click (SET:1130-1134). Manual cleanup, by contrast, has a preview and a two-step confirmation.

### STO-11 — P3 — SMART monitors a guessed device, not the data disk
- The device is the first `/dev/nvme?n?` / `/dev/sd?` / `/dev/vd?` (`SM:96-123`; `SMART_DEVICE` is not set in compose). The UI says "SMART readings from the data drive" (SYS:456), and disk usage is measured on the container's `/` (`M:154`). On a box with a system disk and a separate data disk, the card can report the wrong drive. Suspected on multi-disk hosts. Confirm by comparing `SMART_DEVICE` with `df` of the docker data-root.

### STO-12 — P3 — Lenient SMART evaluation
- Reallocated sectors warn only above 100. NVMe media errors are a warning only, so `healthy` stays True (`SM:223-228, 830-861`). SATA wear reads attribute 177 only (`SM:684-692`), so drives that report wear elsewhere show "Unavailable". Unsupported or unreadable drives correctly report Unknown (`SM:904-917`; SYS:458-485).

## Part 3. Retention deletion logic: what can be deleted, when, and with which guards

**Scheduling.** `storage_loop` runs `StorageManager.run_cycle` in an executor every `STORAGE_CHECK_INTERVAL` (300 s) (`main.py:240-269, 692-695`). `POST /api/storage/prune` runs one more cycle on demand (`S:269-295`); the web UI doesn't use it.

**Each cycle (`M:1706-1815`):**
1. On the first cycle, verify/apply the ISM policy (`M:1720-1725`). See STO-2: it is not retried after an error.
2. **Expired PCAP, at any disk usage** (`prune_expired_pcaps`, `M:776-799`): every `*.pcap` under `PCAP_DIR=/opt/nettap/pcap`, searched recursively (`M:744-767`), with mtime older than `cold_days`. Its `.xxh3` / `.sha256` sidecars are deleted too (`M:770-774`). Held under `_cleanup_lock`. Failures are logged and the loop continues.
3. **PCAP over its share** (`prune_pcaps_over_cap`, `M:801-839`): oldest first until the total PCAP size ≤ `PCAP_MAX_DISK_PCT` (default 25 %) of the PCAP filesystem. **Guard:** the newest file is never deleted (`M:822`). Under the lock.
4. Measure `used/total` of `/` (`M:1735-1743`). If unreadable, the cycle ends with no deletion and no `last_prune_at` update.
5. **≥ 95 % (critical) or ≥ 90 % (emergency) → `emergency_cascade`** (`M:978-1067`):
   - ≥ 95 %: `docker stop nettap-pcap-capture`, and on success write the flag `/opt/nettap/data/storage-stopped-capture` (`M:953-956, 895-908`).
   - If usage ≥ `emergency_threshold`: delete the **oldest PCAP files**, up to 500 per cycle, until usage is < emergency (`M:841-893`). **No newest-file guard, not under the lock** (STO-7). Then, only if still ≥ emergency, run `prune_emergency` (`M:538-618`): every **dated, non-dot index of any tier** (including `unknown`, e.g. `nettap-changelog-*`), oldest name-date first, until usage is < emergency. **Guards:** indices whose name-date is today (UTC) or later are excluded (`M:569-576`). Undated indices (e.g. `arkime_users_v30`, `arkime_files_v30`, OpenSearch "." indices) can never be selected, because both selection and dating come from the index name (`M:340-342, 385-432`). It logs CRITICAL when only today's indices remain (`M:609-617`).
   - If usage is then < 85 % and the flag exists: start pcap-capture again, unless the owner turned capture off in settings (`M:958-976, 1055-1065`).
6. **≥ 80 % (disk_threshold) → `prune_oldest_indices`** (`M:471-532`): only tiers `cold` (other `arkime*`, `sessions*`), `warm` (`suricata*`) and `hot` (`arkime_sessions3*`, `malcolm_beats*`, `zeek*`) (`M:115-119`), in that order. Only indices whose **name-date is older than now − tier retention days** (`M:505-514`). Stops as soon as usage is < 80 %. `unknown`-tier indices are never touched. Under the lock. **Below 80 % the daemon never deletes indices by age:** that is left to ISM.
7. Resume capture below 85 % if this daemon stopped it (`M:1799-1806`). Run the prediction (log only). Stamp `last_prune_at` (`M:1815`).

**ISM (OpenSearch, independent of disk usage).** The policy `nettap-hot-policy` deletes each `arkime_sessions3-*`, `malcolm_beats_*` and `zeek-*` index once its **creation age** reaches `hot_days` (`ilm_generator.py:28, 80-138`). It is attached to new indices through `ism_template` and to existing ones through `add` and `change_policy` (`ilm.py:167-210`). `warm_days` and `cold_days` have no ISM effect. **Yes, ISM and the daemon can both delete the same index.** If one gets there first, the other's delete returns NotFound, which is logged as "Failed to delete index" (`M:463-465`) and is otherwise harmless.

**Manual cleanup** (`POST /api/storage/cleanup/{preview,execute}`, `S:298-411`; `M:1294-1544`): every **dated non-dot index of any tier** with name-date < now − N days and < today (UTC), plus every PCAP with mtime < cutoff. **Guards:** N must be an integer from 1 to 3650 (`S:305-314, 342-351`). Today's index is excluded. A non-blocking lock acquisition returns 409 while a cycle holds the lock (`M:1415-1419`; `S:403-405`). The UI requires a preview and two confirmations and sends the previewed N (SET:813-849). Execute re-computes the set rather than deleting the previewed list. It is written to the changelog as `storage_pruned` (`S:364-400`). **There is no dry-run for automatic deletion.**

**What can never be deleted by retention:** files outside `PCAP_DIR` and anything that isn't `*.pcap` there (device names and pictures, `retention.json`, `.env`, update backups, rules); undated indices; OpenSearch system indices (prefix "."); and, outside an emergency, `unknown`-tier indices.

**What can be deleted that arguably shouldn't be:** NetTap's own changelog (emergency or manual, STO-6); yesterday's index while late records are still arriving (emergency or manual); the PCAP file being written (emergency, STO-7); and every older index the moment retention is shortened (ISM, STO-10).

**Units.** Thresholds are fractions of `used/total` (reserved blocks excluded, STO-3). Byte figures shown in the UI are decimal (1 GB = 10^9 B, `M:1857-1859`; `SYS:33-42`). The PCAP cap is a fraction of the PCAP filesystem's total size (`M:811`).

**Failure surfacing.** All automatic deletion failures are only logged (ERROR or CRITICAL). None reaches the API, the UI or the changelog, and `last_prune_at` is updated regardless (STO-5).
